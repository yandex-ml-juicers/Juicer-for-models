# Лоссы: что есть, как их складывать и как менять веса по ходу обучения

Все лоссы проекта — это `nn.Module` с одним контрактом
(`src/losses/base.py`): forward принимает логиты ученика, логиты учителя,
метки и карты признаков, а возвращает словарь, где `total` — то, по чему
идёт backward, а остальные ключи уезжают в `history.csv` и в ClearML как
компоненты. Лосс сам объявляет, нужен ли ему учитель (`requires_teacher`) и
какие тапы снимать хуками (`required_features`) — тренер настраивается по
этим декларациям.

---

## 1. Лоссы самой сегментации (учитель не нужен)

| Конфиг | Класс | Что делает |
|---|---|---|
| `loss=ce` | `CrossEntropy` | обычная CE, точка отсчёта |
| `loss=dice` | `DiceLoss` | CE + Dice: вклад класса не зависит от его площади |
| `loss=ohem` | `OhemCrossEntropy` | CE только по трудным пикселям кадра |
| `loss=focal` | `FocalLoss` | то же, но непрерывным весом вместо top-K |
| `loss=lovasz` | `LovaszSoftmax` | CE + выпуклое расширение (1 − IoU) |

Зачем они все, если есть CE. На Cityscapes подавляющее большинство пикселей —
уверенно предсказанная середина дороги, неба и зданий; они почти не дают
градиента, но задают среднее. А mIoU считается по классам, где `road` и
`traffic light` равноправны, хотя по площади различаются на два порядка.

- **OHEM** решает первую проблему грубо: считает per-pixel CE и оставляет в
  среднем только пиксели, где вероятность верного класса ниже `thresh`,
  но не меньше `keep_ratio` доли самых трудных на КАЖДОМ кадре (иначе один
  трудный кадр батча забрал бы всю квоту). Отбор идёт по порогу
  `min(k-й по величине лосс, -log(thresh))` — это и есть min_kept из
  mmsegmentation, только выраженный долей, а не числом пикселей.
- **Focal** решает её же гладко: множитель `(1 - p_true)^gamma` глушит лёгкие
  пиксели, ничего не выбрасывая. `gamma=0` — обычная CE. Веса классов
  (`alpha`) — список длины `num_classes` или `null`.
- **Dice** и **Lovász** решают вторую. Dice нормируется на площадь класса,
  Lovász — точное выпуклое расширение (1 − Jaccard), то есть единственный
  лосс, который минимизирует ровно ту величину, которой меряется качество.
  Плата: Lovász сортирует все пиксели по каждому классу, поэтому у него есть
  `pixel_stride` (по умолчанию 2 — вчетверо меньше элементов, оценка Jaccard
  не меняется).

Чистыми `Lovász` и `Dice` не обучают: у почти случайной модели у них нет
внятного градиента. Поэтому у обоих есть `ce_weight`.

## 2. Дистилляционные лоссы

| Конфиг | Класс | По чему дистиллирует |
|---|---|---|
| `loss=pixel_kd` | `PixelWiseKD` | логиты, KL по классам в каждом пикселе |
| `loss=cwd` | `ChannelWiseKD` | логиты, softmax по пространству внутри канала |
| `loss=dist` | `DISTLoss` | логиты, корреляции вместо точных значений |
| `loss=fitnets` | `FitNetsKD` | карты признаков через обучаемый регрессор |
| `loss=mgd` | `MGDLoss` | карты признаков через восстановление замаскированного |
| `loss=bpkd` | `BPKDLoss` | логиты, отдельно граница и тело объекта |
| `loss=heteroakd` | `HeteroAKDLoss` | признаки, спроецированные в пространство классов |

### BPKD (arXiv:2306.08075)

Граница и тело объекта требуют разного знания. В теле важна форма — крупная
связная область одного класса; на границе важно попиксельное различение
соседних классов, и именно там компактный ученик ошибается чаще всего.
Дистиллировать их одним лоссом — значит усреднять два разных требования.

Граница берётся морфологической разностью по разметке (`dilation - erosion`,
в реализации это max-pool против min-pool с окном `edge_width`), после чего:

- `L_edge` — попиксельная KL по классам, усреднённая **только по граничным
  пикселям**;
- `L_body` — канальная KL, как в CWD, но граничные пиксели исключены из
  пространственного softmax.

Веса в конфиге (`edge_weight`, `body_weight`) сопоставимы с `alpha` у
pixel-KD и `cwd_weight` у CWD. Числа 50/20 из статьи сюда переносить нельзя:
там нормировка суммами по кадру, здесь — средними.

### HeteroAKD (arXiv:2504.07691)

Метод для пары «разные архитектуры» — ровно наш случай SegFormer → U-Net.
Промежуточные признаки трансформера и свёрточной сети живут в несопоставимых
пространствах, и FitNets в такой паре заставляет ученика воспроизводить
особенности чужой архитектуры, а не знание о сцене.

Три шага:

1. **Общее пространство.** Признаки обеих моделей проецируются 1x1-свёрткой
   в пространство классов (канал на класс). Архитектурная специфика при этом
   отбрасывается.
2. **KMM.** Надёжность каждой проекции меряется бинарной кросс-энтропией с
   разметкой, и таргет собирается смесью: где учитель увереннее прав — его
   значение, где хуже ученика — сдвиг к ученику. То есть ошибки учителя
   ученику не навязываются.
3. **KEM.** Веса пикселей — по тому, насколько ученик отстаёт от собранного
   таргета; там, где не отстаёт, учить нечему.

`proj_weight` — супервизия проекторов разметкой. В статье отдельным членом
она не выписана, но без неё «пространство логитов» ничем не закреплено за
классами, а проектор учителя вовсе не получает градиента (таргет отсоединён
от графа) и под DDP роняет шаг.

Каналы в конфиге (`student_channels`, `teacher_channels`) — ширины того тапа,
который указан в `layer`; по умолчанию это `taps.stage4`.

## 3. Несколько лоссов сразу — `CompositeLoss`

Тренер знает один criterion, поэтому «CE + FitNets + Dice» собирается лоссом,
а не тренером:

```yaml
_target_: src.losses.CompositeLoss
_convert_: all

losses:
  kd:
    _target_: src.losses.FitNetsKD
    ce_weight: 0.0          # CE живёт в одном месте, см. ниже
    hint_weight: 1.0
    layers:
      taps.stage3: { student_channels: 112, teacher_channels: 320, weight: 1.0 }
    ignore_index: ${data.dataset.ignore_index}
  seg:
    _target_: src.losses.DiceLoss
    ce_weight: 1.0
    dice_weight: 1.0
    ignore_index: ${data.dataset.ignore_index}

weights:
  kd: 0.7
  seg: 0.3
```

Готовый пример — `loss=composite_fitnets_dice`, полный эксперимент с ним —
`segmentation/FitNets/cityscapes_FitNets_dice_ohem_segformer_b2_to_unet_small`.

Что композиция делает сама:

- объединяет требования слагаемых: учитель нужен, если он нужен хотя бы
  одному; хуки ставятся на объединение `required_features` (по одному хуку
  на слой, даже если тап просят двое);
- регистрирует слагаемые в `ModuleDict`, поэтому их обучаемые параметры
  (регрессор FitNets, проекторы HeteroAKD) видны через
  `criterion.parameters()` и попадают в optimizer;
- разводит ключи логов: `kd_hint`, `seg_dice`, а сами `total` слагаемых —
  под именами `kd`, `seg`.

**Главное правило: CE должна остаться ровно в одном слагаемом.** Почти
каждый лосс считает её сам, и без обнуления `ce_weight` она войдёт в сумму
дважды с непонятным итоговым весом. OHEM и Focal — это тоже CE, только
переваженная: если в композиции есть один из них, у остальных `ce_weight: 0`.

## 4. Расписание весов — `loss_schedule`

Дистилляция полезна, пока ученик слабее учителя, и мешает в конце, когда он
уже у своего потолка, а учитель тянет его к своим ошибкам. Симметричный
случай — прогрев: hint-лосс FitNets разумно придавить на первых эпохах, пока
регрессор внутри лосса сам не обучился.

```yaml
loss_schedule:
  hint_weight:   {schedule: cosine, start: 0.7, end: 0.0, start_epoch: 120}
  ce_weight:     {schedule: cosine, start: 0.3, end: 1.0, start_epoch: 120}
  weights.kd:    {schedule: linear, start: 1.0, end: 0.0}   # слагаемое композиции
  losses.kd.temperature: {schedule: constant, start: 1.0}
```

Ключ — путь к весу внутри лосса: атрибут (`hint_weight`), элемент
`weights` у композиции (`weights.kd`) или атрибут слагаемого
(`losses.kd.ce_weight`). Расписания: `constant`, `linear`, `cosine`;
вне отрезка `[start_epoch, end_epoch]` вес держится на границе,
`end_epoch: null` означает «до конца обучения».

Никакой поддержки со стороны лоссов не требуется: все они хранят веса
обычными float-атрибутами и читают их в forward, поэтому расписание —
это присваивание перед эпохой. Пути проверяются при старте, а не при первом
применении: опечатка иначе всплыла бы через час обучения, причём молча.

Текущие значения уходят в `history.csv` колонками `loss_weight_*` и в
ClearML на график `loss_weights` — без него падение дистилляционного члена
не отличить от того, что ученик догнал учителя.

## 5. Мультимасштабный учитель — `model.teacher_inference`

```yaml
model:
  teacher_inference:
    scales: [0.75, 1.0, 1.25]
    flip: true
```

Учитель прогоняется в нескольких масштабах и с отражением, предсказания
усредняются по вероятностям и возвращаются на исходную сетку. На Cityscapes
это стабильно даёт +1..2 mIoU самому учителю — то есть ученик учится по
более чистым таргетам за ту же цену обучения.

Стоимость: по лишнему прогону учителя на каждую пару (масштаб, отражение) —
в примере выше шесть вместо одного. Учитель и так под `no_grad`, но эпоха
удлиняется заметно.

Две детали реализации, о которых стоит знать:

- наружу отдаются **логарифмы усреднённых вероятностей**, а не логиты. Для
  softmax внутри KD это одно и то же с точностью до константы, но при
  `temperature != 1` масштаб меняется — температуру, возможно, придётся
  подобрать заново;
- масштаб 1.0 прогоняется последним и без отражения: forward-хуки
  срабатывают на каждом прогоне, и в карты признаков (их берут FitNets,
  MGD, HeteroAKD) обязан попасть кадр родного разрешения.
